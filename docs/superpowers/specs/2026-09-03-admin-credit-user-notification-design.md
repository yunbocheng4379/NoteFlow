# 管理员调整电力后的用户站内通知设计

## 背景

当前管理员可以通过“电力管理”对单个用户或批量用户增加、扣除电力。操作会写入电力流水，但目标用户只能在流水页看到变化，无法在“我的通知”中主动获知管理员调整。

本次优化在不改变电力账本规则的前提下，为每个受影响用户新增一条站内通知。

## 目标与非目标

### 目标

- 单个管理员调整成功后，目标用户收到一条“我的通知”。
- 批量管理员调整成功后，每位目标用户各收到一条通知。
- 通知说明本次变动方向与数量、调整后余额和管理员备注。
- 通知以电力流水 ID 幂等，避免同一笔调整重复产生通知。
- 通知写入异常不影响已经成功提交的电力账务结果。

### 非目标

- 不新增通知表、通知查询 API 或新的异步队列。
- 不改变电力流水、余额校验、事务提交和批量全量回滚规则。
- 不增加邮件、推送或浏览器通知。

## 方案

采用“账务提交成功后调用现有站内通知服务”的方案。

管理员调整接口先按现有逻辑调用 `credit_ledger.admin_adjust` 并提交数据库事务。提交成功后，使用刚创建的流水和目标用户信息调用 `UserNotificationService.publish`。通知服务使用独立会话写入 `user_notifications`，这样通知写入失败不会回滚已经成功的电力调整。

单个调整直接发布一条通知；批量调整在账务事务成功提交后遍历每条流水，分别向对应用户发布通知。批量账务仍然保持现有“一名用户余额不足则整体回滚”的规则。

## 通知数据

每条通知使用以下固定字段：

| 字段 | 值 |
| --- | --- |
| `category` | `credit_adjustment` |
| `source_type` | `credit_transaction` |
| `source_id` | 对应电力流水的 `transaction_id` 字符串 |
| `title` | `电力余额已调整` |
| `link` | `/billing?tab=transactions` |
| `severity` | 增加电力为 `info`，扣除电力为 `warning` |

正文格式表达以下信息：

```text
管理员已为你的账户增加 520 电力。
调整后余额：3401 电力
备注：活动赠送
```

扣除场景将“增加”替换为“扣除”，数量使用绝对值；余额和备注使用本次电力流水的实际结果。

## 实现边界

- 在 `backend/app/routers/admin_credits.py` 中增加内部通知辅助函数，统一单个和批量接口的通知构造逻辑。
- 辅助函数复用 `UserNotificationService.publish`，并捕获、记录通知异常。
- 单个接口在 `db.commit()` 成功且重新取得用户后发布通知。
- 批量接口在 `db.commit()` 成功且取得所有用户后逐项发布通知；单个通知失败时继续处理剩余用户。
- 在 `NoteFlow_frontend/src/pages/NotificationsPage/index.tsx` 的分类映射中增加 `credit_adjustment: '电力调整'`。
- 不修改现有用户通知列表、已读、未读计数和详情交互。

## 异常处理与幂等

- 电力调整失败：沿用现有错误处理，回滚账务且不发布通知。
- 电力调整提交成功、通知写入失败：保留账务结果，记录包含用户 ID 和流水 ID 的日志，不向管理员报告账务失败。
- 通知重复调用：由于 `user_id + category + source_type + source_id` 唯一约束，使用流水 ID 可定位同一笔调整；重复调用更新原通知而不是新增通知。
- 批量账务在提交前发生任何调整错误：沿用现有整体回滚，不产生任何通知。

## 测试与验收

后端测试覆盖：

1. 单个正向调整成功后，目标用户存在一条对应通知，正文包含增加数量、调整后余额和备注，级别为 `info`。
2. 单个负向调整成功后，通知正文使用扣除语义，级别为 `warning`。
3. 批量调整成功后，每位目标用户各有一条通知，且每条通知关联各自的电力流水。
4. 通知服务抛出异常时，管理员调整接口仍返回成功，余额和电力流水保持已提交状态。
5. 调整失败或批量回滚时，不产生用户通知。

前端验收：

- “我的通知”列表和详情将该通知显示为“电力调整”。
- 点击“查看相关内容”可进入用户电力流水页。
- 前端构建通过，现有用户通知页面行为不变。
